# Безопасность, разграничение прав и защита данных (152-ФЗ)

Документ регламентирует модель угроз, механизмы аутентификации, разграничения доступа (RBAC), минимизацию персональных данных и правила аудита платформы «Лёгкие на подъём».

---

## 1. Соответствие 152-ФЗ и медицинская специфика

### Минимизация данных (Data Minimization)
В соответствии с требованиями Федерального закона № 152-ФЗ «О персональных данных» в контуре системы **полностью исключён сбор прямых персональных данных детей**:
1. **Без ФИО и даты рождения**: в БД хранятся только сгенерированные или согласованные псевдонимы («Миша К.», «Тимофей Р.») и целочисленный возраст (лет).
2. **Без контактов родителей**: телефоны, адреса и email законных представителей не собираются в приложении.
3. **Без хранения сырого аудио**: микрофонный сигнал анализируется исключительно на клиентском устройстве в реальном времени. Временные PCM-буферы и FFT-массивы не сохраняются на диск, не буферизуются в Blob и не передаются по сети. На сервер отправляются только агрегированные числовые метрики сессии (число выдохов, процент правильности, средняя длительность).

### Документооборот
* Шаблон согласия родителя на обработку данных и проведение игровых дыхательных упражнений находится в файле `docs/PARENTAL_CONSENT_TEMPLATE.md`.
* Публичная политика конфиденциальности приведена в `docs/PRIVACY_POLICY.md`.

## 2. Модель ролей и управление доступом (RBAC)

Система поддерживает 3 роли с жёстким разграничением полномочий на уровне API:

```
[Пользователь] ──> [auth_sessions (httpOnly Cookie)]
                          │
         ┌────────────────┼────────────────┐
         ▼                ▼                ▼
     [ Admin ]     [ Specialist ]   [ Demo Specialist ]
         │                │                │
         │                │                └──> Read-Only к демо-пациентам
         │                │                     (POST/PUT/DELETE -> 403 Forbidden)
         │                │
         │                └──> Доступ ТОЛЬКО к пациентам из `patient_access`
         │                     (GET /api/v1/patients/:id -> 403 если нет связи)
         │
         └──> Управление организациями и специалистами, аудит
```

### 1. `admin` (Администратор)
* Управление организациями (`organizations`) и учетными записями специалистов (`users`).
* Назначение связей между специалистами и пациентами в `patient_access`.
* Просмотр журнала событий информационной безопасности (`audit_events`).
* Не имеет публичной регистрации; первый администратор создаётся при инициализации системы.

### 2. `specialist` (Специалист / Врач-пульмонолог / Инструктор ЛФК)
* Вход по email и паролю.
* Видит в `GET /api/v1/patients` **только тех пациентов**, которые явно привязаны к нему в таблице `patient_access`.
* Попытка запросить карточку чужого пациента (`GET /api/v1/patients/:id`) или назначить задание (`POST /api/v1/patients/:id/assignments`) перехватывается серверным middleware `requirePatientAccess` и **возвращает `403 Forbidden`** с записью инцидента в `audit_events`.
* Возможность смены собственного пароля (`POST /api/v1/auth/change-password`).

### 3. `demo_specialist` (Демо-специалист)
* Доступен через эндпоинт `POST /api/v1/demo/session` для ознакомления с возможностями кабинета.
* Имеет доступ к синтетическому демо-контуру (5 клинических сценариев).
* **Строго Read-Only**: попытка любого изменения (создание назначения, смена пароля и др.) отклоняется с кодом `403 Forbidden`.

## 3. Криптография и сессии

### Хэширование паролей
* Алгоритм: криптостойкая функция формирования ключа `scrypt` из стандартного модуля `node:crypto`.
* Параметры:
  - Коэффициент затрат времени $N = 16384$;
  - Размер блока $r = 8$;
  - Параллелизм $p = 1$;
  - Длина ключа: 64 байта;
  - Длина соли: 16 случайных байт (`crypto.randomBytes(16)`).
* Формат хранения в БД: `${salt.toString('hex')}:${derivedKey.toString('hex')}`.
* Сравнение хэшей при аутентификации выполняется через `timingSafeEqual` для защиты от атак по времени (timing attacks).

### Сессии
* Серверные сессии хранятся в таблице `auth_sessions`.
* Клиенту передаётся случайный криптографический токен в `httpOnly`, `SameSite=Lax` cookie `legkie_session`.
* В базе данных сохраняется только криптографический хэш токена (`SHA-256`), что предотвращает компрометацию сессий даже в случае прямого чтения дампа БД.
* В production-окружении обязателен флаг `Secure` (передача исключительно по HTTPS).

### Защита от перебора (Rate Limiting)
* Эндпоинт `/api/v1/auth/login` защищён ограничителем запросов (максимум 5 неудачных попыток за 15 минут на связку `IP + email`).
* При превышении лимита возвращается `429 Too Many Requests`.

## 4. Аудит действий и безопасность логов

Журнал `audit_events` фиксирует все ключевые события:
* Входы в систему (`login`), выходы (`logout`), отказы в авторизации (`failed_login_attempt`);
* Просмотры карточек пациентов (`view_patient_detail`);
* Создание версий назначений (`create_assignment`);
* Попытки несанкционированного доступа к чужим пациентам (`unauthorized_patient_access_attempt`);
* Попытки мутаций в демо-режиме (`forbidden_mutation_attempt`).

### Политика отсутствия ПДн в аудит-логах
* В колонку `audit_events.details` **категорически запрещено** записывать:
  - Email пользователя;
  - Псевдонимы и имена пациентов;
  - Диагнозы и медицинские заключения.
* В `details` допускаются только технические метаданные: `{ "method": "POST", "patientId": "UUID", "count": 10 }`.
* Фиксация IP-адреса производится исключительно для целей расследования инцидентов ИБ и предотвращения сетевых атак, о чём явно указано в Политике конфиденциальности.
